AI Supply Chain Intelligence Platform

A small logistics team already has the data to know which vendors are failing them. What they have instead is a folder of spreadsheets exported from systems that agree on nothing. This turns any one of those files into a risk report they can act on — and defend.

The decision
everything hangs on

Every number in this product is computed in Python. The model never calculates anything.

The obvious version of this product hands the spreadsheet to an LLM and asks what's wrong. I think that version is broken in a specific way: a model asked to compute a late rate returns a number that looks right, can't be checked, and changes on the next run.

So the analytics engine is pure Python with no I/O — KPIs, vendor health, country risk, and a weighted composite score. Claude receives those finished metrics and explains them, under a prompt that requires every risk it raises to name the exact computed field behind it. Three things fall out: the dashboard survives an outage of the model, because metrics are persisted before the call is made; any score can be recomputed and audited; and cost scales with datasets rather than rows.

Interface
decisions

I cut the world map.

Geographic exposure was going to be a choropleth. It was the wrong call: most uploads cover three to ten countries, so the map is mostly empty ocean, it shrinks to unreadable in a dashboard tile, and it costs a large vendored map file to render. A ranked panel carries volume share, risk score, and average delay per country in the same space and stays legible at any size. The map would have looked better in a screenshot and served the user worse.

A missing value renders as a dash and a reason, never a zero.

If a file has no price column, showing $0 is a lie shaped like a measurement. An em dash is less satisfying to look at and far more honest, and honesty is the entire value of a screen someone makes decisions from.

Partial failure is a designed state, not an error page.

The AI summary can fail while the computed metrics are perfectly fine. So a failed summary renders a banner that says explicitly that the numbers below it are unaffected, and the rest of the page stays live. Loading, empty, error, and partially-degraded are built as real components, because on a data product those are the states users actually spend their time in.

Every AI-written claim shows its evidence.

Each risk displays the specific metric it rests on, directly beneath it. A recommendation with no visible basis is something a user either accepts blindly or ignores entirely, and neither is useful.

Engineering
decisions

The most important column is usually the one that isn't there.

Almost no real export carries a delay column. It carries a promised date and an actual date and expects you to subtract. Before I derived it, every shipment read as on time, the risk score came out zero, and the dashboard was confidently wrong — the worst failure available to a data product. Delay is now derived across eighteen date formats, and the count of derived values is reported back to the user, because a number the system invented should never be indistinguishable from one the file supplied.

Measure before you rewrite.

Three hundred thousand rows took 84 seconds, and I assumed the cost was structural. It was an exception handler: matching one of eighteen date formats means raising and catching an error for every format ahead of the right one, twice per row — about three million exceptions. A year of shipments contains only a few hundred distinct date strings, so caching the format lookup collapsed it. Same file, 14 seconds.

Degrading gracefully is not the same as degrading cheaply.

With Redis down the app technically fell back to “no cache” — while the client library silently retried every refused connection, so a single page paid about eight seconds. A circuit breaker now opens after three consecutive failures. It also cut the test suite from 146 seconds to 22. The Celery broker had the uglier version of the same problem: with it down, uploads hung indefinitely, and disabling the connection loop globally would have stopped a live worker from ever reconnecting. The API now probes the broker itself before publishing and falls straight through to in-process execution. Hanging uploads became a response in 1.4 seconds.

One canonical model, many source schemas.

Real companies receive shipment data from dozens of ERP, WMS, TMS and carrier systems. So the app doesn't parse a format — it maps any export onto one 50-field canonical record through roughly 350 aliases and a deliberately conservative fuzzy pass, because a wrong mapping is far worse than an unmapped column: it silently feeds bad numbers into every metric downstream. When an alias collision let one field quietly swallow another's data, I wrote a test that walks the entire table and fails on any header claimed twice. It found two more dead entries.

Double DQN — Lunar Lander

A reinforcement learning agent trained from scratch to land the Gymnasium LunarLander-v3 craft, with experience replay, a soft-updated target network, a multi-seed experiment harness, and an ablation against vanilla DQN. The ablation contradicted the result I expected.

What the
ablation found

Double DQN is the change most widely recommended for a vanilla DQN. On my configuration it lost to the baseline, decisively.

Across seeds 42, 43 and 44 at 700 episodes each, vanilla DQN scored 272.4 ± 1.4 and solved the environment on 3 of 3 seeds. Double DQN scored −453.8 ± 471.6 and solved 1 of 3. A random policy scores −177.6, so two of the three Double runs finished well below doing nothing at all.

The average hides the shape of it. Vanilla's three seeds landed within 3.1 points of each other — not just better, but stable. Double was bimodal: one seed solved it, two diverged outright.

Reading it
honestly

A loss growing without bound while the score collapses is Q-value divergence — the estimates run away, the policy follows them, and the lander ends up flying off firing engines. Double DQN didn't fail to learn here. It learned, then came apart.

My first assumption was a bug in my own code. It isn't: the implementation matches the standard formulation, and the suite covers exactly that path — Double against vanilla target selection, and the one-sided overestimation gap between them. All 42 tests pass.

So I have two hypotheses and no way to choose between them yet. Either three seeds got unlucky, or the soft target update is the culprit — τ = 0.005 after every gradient step keeps the target network close to the policy network, and Double DQN's benefit depends on their errors being uncorrelated. Running more seeds separates those, and it's the next thing I'd do.

What I didn't do is drop the arm and report the result I expected.

What I owned

This began as a coursework assignment built by three of us: I wrote the Q-network architecture, the agent — action selection, the Bellman update, target maintenance — and the training loop. Attribution for every module is preserved in its docstring.

The rebuild from that submitted notebook into a reproducible repository is entirely my own, and it is the part I'd want to be judged on.

Why a notebook
wasn't enough

The assignment trained an agent and printed some numbers. Every one of those numbers was unreproducible, and it took me a while to see why.

Nothing was ever saved.

The notebook defined functions to persist and load weights and never called either one, so every evaluation silently retrained the agent first.

The evaluation moved every time you ran it.

It scored ten unseeded episodes, sampling different starting conditions on each run. Evaluation is now a hundred episodes seeded from a fixed offset, disjoint from the training seeds.

A single run is close to meaningless.

The same reinforcement learning code on a different seed can plateau at 40 or reach 250. Results are now reported as mean and spread across seeds, against a random-policy floor measured on identical seeded episodes, so a score has something to be measured against. Every figure serialises to a JSON file written by the run that produced it.

There was also a hyperparameter defined but never read, implying a periodic hard target update that was not happening. Removing it was a documentation fix disguised as a code change.

The test
worth writing

Omitting the terminal-state factor from the Bellman target is the classic DQN bug: training still runs, the loss still falls, and the agent quietly never learns to land.

That is the failure mode the suite exists for — the bugs that produce a plausible-looking agent rather than a crash. Tests cover the Bellman target with and without terminal transitions, Double against vanilla target selection, the one-sided overestimation gap between them, soft-update arithmetic, and that a gradient step moves the policy network and not the target. CI adds a smoke job that runs two real training episodes against the actual environment, because unit tests mock the environment away and can't catch a broken artifact write.

The ablation harness trains both Bellman variants under matched seeds and episode budgets, so the target computation is the only thing that differs between the arms.

How I work

01

A number I can't defend is worse than no number.

Both of these projects converged on the same rule from different directions: show the evidence, name the source, and say plainly when something is unknown. A confident wrong answer costs more than a visible gap, and it costs it later, when someone has already acted on it.

02

Find where the time actually goes before restructuring anything.

The 84-second parse and the 8-second cache miss were both hiding somewhere I would not have guessed, and both fixes were small once I stopped guessing. I'd rather spend an hour measuring than a day rewriting the wrong layer.

03

Ship something that survives being handed to someone else.

Tests, CI, a runbook, and a README that explains the reasoning rather than the syntax. It's the difference between a demo and a thing that still works in three months, and it is most of what I've taught myself this year.
